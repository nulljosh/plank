# Architecture

One file does the work. Everything else is examples, tests and docs.

| File | What it does |
|---|---|
| `plank.py` | The compiler. `lex` turns source into tokens (`string_end` and `unescape` handle strings and `\(...)` interpolation), `Parser` builds the AST (dataclasses near the top), `Codegen` walks the AST once and emits LLVM IR through llvmlite, `optimize` runs the O2 pipeline, `build` links the object with `cc`. `JSON_SRC` is the `Json` enum written in Plank, parsed in front of every program; `json_reader` emits the parser for it in IR against a cursor the runtime keeps. `RUNTIME` is a C string, compiled next to every program, holding what libc does not: joining strings, counting characters, number to text and back, reading a line, string tools (split, join, trim, replace, slices, all counting UTF-8 characters), `popen` for `run`, curl for `http`, a JSON lexer, growing lists, a stable merge sort that calls back into compiled code, and dicts: insertion-ordered entry arrays under an open-addressing index, keys stored as 8 bytes (an int or a string pointer). Every list is one C struct of length, capacity and bytes; the compiler knows the element type, the runtime only its size. Bounds checks are inline IR, so the hot path never calls out. `main` is the CLI. |
| `plank` | Symlink to `plank.py` so `./plank file.pk` works. The `uv run --script` shebang installs llvmlite on first use. |
| `examples/*.pk` | One program per feature: hello, fib, fizzbuzz, primes, sqrt, strings, text, lists, structs, dicts, enums, optionals, closures, textkit, world, errors, scripting, generics, containers, collections, loops. `examples/lib/` holds files that get imported rather than run. Each has a `.out` with its expected output. |
| `apps/*.pk` | Seven real programs: a tool-using agent loop that talks to Ollama over HTTP and JSON, a calculator with its own parser, a to-do CLI that saves to a file, word frequency, a budget ledger, a maze solver, Game of Life. Each has a `.out`; `test.py` runs them like the examples and the landing shows their output. |
| `tests/*.pk` | The language testing itself: strings, lists, dicts, types, control. Each is a Plank program full of `assert` that prints `ok`. |
| `list_helper` in `plank.py` | first, last, index_of, insert, remove_at, reverse, sum, min, max on lists, mostly inline IR; min and max sort a copy and take an end. |
| `plank test [dir]` | Built into the CLI: compiles every `.pk` in the folder and passes it when it exits 0 printing `ok`. `test.py` is the repo's own suite; `plank test` is for programs written in Plank. |
| `test.py` | Compiles every example, diffs the output, and runs every `tests/*.pk`, checks 27 error messages at compile time and run time, then runs everything again with the collector firing every 4KB. CI runs it on macOS and Ubuntu. |
| `docs/SPEC.md` | The language reference. |
| `docs/HACKERS-AND-PAINTERS.md` | Paul Graham's book summarized, and the eight design rules Plank takes from it. |
| `docs/COMPARE.md` | The scorecard against Python, Ruby and Swift. The roadmap works down it. |
| `site/index.html`, `site/icon.svg`, `wrangler.toml` | The landing page at plank.heyitsmejosh.com, deployed as Cloudflare static assets. Drifting-plank canvas, hero, and a demo window that plays the real examples. |
| `tools/gen-demo.py`, `site/demo.js` | The generator reads every example, its `.out`, and `plank emit` output into `demo.js`. `test.py` fails if `demo.js` is stale, so the landing can never show output the compiler did not produce. |
| `roadmap.md`, `MONEY.md`, `CLAUDE.md` | What is next, what it earns (nothing, on purpose), and notes for the agent. |

## The pipeline

Source goes through four steps, each a plain function or class:

1. **Lex.** One regex, a loop, a list of tokens. Strings get a small hand scanner instead, because `\(...)` can hold strings of its own. `unescape` decodes escapes, keeps UTF-8 intact, and hands interpolations back as source for the parser. Newlines are tokens so statements can end without semicolons; inside parentheses they are dropped.
2. **Parse.** `load` parses the main file and every file it imports, once each. Lines in the k-th file are numbered from k million, so a single line number carries the file too, and `locate` turns it back into a path and a line for every error, compile time or run time. Recursive descent for statements, Pratt for expressions. Precedence lives in one dict.
3. **Codegen.** `program` names every struct first, so fields can mention structs declared later, then declares every function and method (`Point.length` becomes `pk_Point.length` with `self` as its first argument), then fills in the bodies. A struct value is a pointer to a heap LLVM struct. An enum value is a pointer to a tag and enough 8-byte slots for its biggest case; `match` on an enum is one LLVM `switch` on the tag, and the compiler counts the cases it saw to refuse a match that misses one. `arrange` lines up positional and labeled arguments and fills defaults, for calls and struct building alike. A generic function is kept as its AST; `call_generic` evaluates the non-closure arguments, `unify` matches their types against the parameter types to bind each type parameter, `specialize` deep-copies the AST with the names substituted, and the copy is compiled once per distinct binding under a name like `first<int>`. Generic structs work the same way through `instantiate_struct`: `Stack<int>` becomes a real struct, with its methods compiled as `Stack<int>.push`, the first time the name is used in a type or a call; `Stack(items: [1])` binds `T` from the fields with the same `unify`. An optional `T?` is a pointer to a boxed `T`, null for `nil`; `coerce` does the boxing wherever a value lands in an optional slot (let, assignment, return, arguments, append). A closure is a pointer to two words, code and environment; the environment is an array of pointers to the variables it uses. `captures` scans each function for names any lambda mentions, and `declare` puts exactly those variables on the heap so a closure can outlive the call. A top-level function used as a value gets a constant closure around a small wrapper. A closure with no `->` is compiled once as a probe, where the first `return` sets the type, then thrown away and compiled for real. `match` as a value is parsed into a closure around a `match` statement whose arms `return`, so one code path handles both, at the price of a closure call. `try` calls `setjmp` through the runtime's stack of handlers; `pk_panic`, which every runtime error goes through, `longjmp`s to the newest one instead of exiting. A function that contains a `try` keeps all its variables in memory rather than registers, so values set before a throw are still there after it, and `return`, `break` and `continue` pop the handlers they jump out of. There is no separate type checker. Every expression returns a pair of LLVM value and Plank type, and the operator and call rules check the types as they go. Variables are `alloca` slots; LLVM's mem2reg turns them into registers at O2.
4. **Optimize and link.** llvmlite's new pass manager at O2, then the target machine emits a Mach-O or ELF object, and the system `cc` links it with `RUNTIME`, libc and libm. `RUNTIME` opens with the collector: every allocation carries a header naming its slot in a table; a collection sorts the table by address, scans the stack, the registers (spilled with `setjmp`) and the open `try` frames for words that point into a block, follows those through every non-string block, and frees what was never reached. Strings are marked atomic and never scanned. Runtime helpers that hold a caller's pointer only in a C local bump `pk_hold` so no collection can run under them; the stress mode in `test.py` is what found that this was needed. A collection runs once as many bytes have been allocated as survived the last one, so a steady program keeps a steady footprint. The generated C `main` hands `argc` and `argv` to the runtime for `args()`. Nothing is freed yet: programs run and exit, and the OS takes the memory back.

User functions are named `pk.name` in the IR, methods `pk.Type.name`. The dot cannot appear in a C name, so nothing you call a function can collide with libc or the runtime's `pk_` helpers. A generated C `main` calls `pk.main` and returns 0.
